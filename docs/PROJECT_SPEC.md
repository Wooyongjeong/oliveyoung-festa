# 페스타 현장 수령 티켓 판매 시스템

## 1. 과제 개요

오픈 시점에 트래픽이 집중되는 환경에서 페스타 입장 티켓을 선착순으로 판매하는 풀스택 MVP를 구현한다.

사용자는 남은 티켓을 확인하고 구매를 요청한다. 시스템은 결제가 확정될 때까지 재고를 임시 점유하고, 여러 PG 중 하나를 선택해 Mock 결제를 수행한다. 결제가 실패하거나 점유가 만료되면 재고를 정확히 복구해야 한다. 백엔드는 같은 저장소를 공유하는 여러 인스턴스로 실행되어도 초과 판매가 발생하지 않아야 한다.

핵심 평가 대상은 화면의 화려함보다 다음 세 가지다.

1. 동시 요청에도 판매 수량이 실제 재고를 넘지 않는가
2. 지연·실패·재시도·만료 상황에서도 주문과 재고가 일관적인가
3. 그 동작을 자동화 테스트와 실행 가능한 증거로 설명할 수 있는가

## 2. 해석 및 가정

원문에서 모호한 부분은 MVP 구현을 위해 다음과 같이 해석한다.

- `티켓 2장`은 기본 전체 재고가 2매라는 의미로 본다. 단, 일반/VIP 등급별 초기 재고는 설정으로 변경할 수 있다.
- 좌석을 지정하지 않는 자유 입장 행사이며, 결제 성공 시 현장에서 사용할 수 있는 전자 티켓을 발급한다.
- 한 사용자는 한 이벤트에서 등급과 관계없이 최대 1매만 구매할 수 있다.
- 선착순 기준은 결제 완료 시각이 아니라 대기열 입장 순서와 재고 점유 순서다. 결제 지연 때문에 뒤 사용자가 순서를 빼앗지 않는다.
- 점유 유효 시간의 기본값은 3분이며 설정 가능하다.
- 결제 성공 후 환불하면 아직 사용하지 않은 티켓에 한해 재고를 다시 판매 가능 상태로 돌린다.
- Mock PG의 평균 응답은 1초 이내이며, 실패율·지연·실패 사유를 설정 또는 테스트 입력으로 제어할 수 있다.
- 실제 개인정보, 실제 결제 정보, 실제 PG 연동은 범위에서 제외한다.

위 가정은 구현 전에 변경할 수 있다. 특히 **등급별 기본 재고**, **1인 제한 범위**, **환불 시 재판매 여부**는 최종 확인이 필요한 정책이다.

## 3. 사용자 역할

### 고객

- 로그인한다.
- 판매 이벤트와 일반/VIP 잔여 수량을 확인한다.
- 대기열에 진입하고 입장 허가를 받는다.
- 원하는 티켓 등급 1매를 구매한다.
- 결제 실패 사유를 확인하고, 조건이 허용되면 다시 시도한다.
- 주문 내역과 발급된 티켓을 확인한다.
- 미사용 티켓을 취소/환불한다.

### 현장 운영자

- 티켓 코드를 조회 또는 스캔한다.
- 티켓의 행사, 소유자, 상태, 사용 가능 여부를 확인한다.
- 유효한 티켓을 1회 입장 처리한다.
- 이미 사용·취소·만료된 티켓의 중복 입장을 차단한다.

### 관리자

- 판매 현황과 주문/결제 이력을 확인한다.
- 개발·시연 환경의 데이터를 초기 상태로 리셋한다.

## 4. 핵심 업무 규칙

### 4.1 이벤트와 재고

- 이벤트는 판매 시작/종료 시각과 행사 시각을 가진다.
- 티켓 등급은 최소 `GENERAL`, `VIP`를 지원한다.
- 등급별로 `총수량`, `점유수량`, `판매수량`, `가용수량`을 관리한다.
- 항상 `가용수량 = 총수량 - 유효 점유수량 - 판매수량`이어야 한다.
- 어떤 동시성 상황에서도 가용수량과 각 수량은 음수가 될 수 없다.
- 판매 기간 밖이거나 매진이면 새 점유를 만들 수 없다.

### 4.2 대기열과 선착순

- 판매 오픈 전에는 구매를 허용하지 않는다.
- 오픈 후 대기열 토큰을 발급하며, 토큰에는 사용자와 순번이 연결된다.
- 제한된 수의 사용자만 일정 시간 동안 구매 API에 접근할 수 있다.
- 활성 토큰은 다른 사용자가 사용할 수 없고 만료된다.
- MVP의 공정성은 서버가 대기열 요청을 원자적으로 기록한 순서로 정의한다. 네트워크상 실제 클릭 시각까지 보장하지는 않는다.

### 4.3 주문과 점유

- 유효한 입장 토큰을 가진 로그인 사용자만 주문을 생성할 수 있다.
- 주문 생성과 재고 점유는 하나의 원자적 작업이어야 한다.
- 점유 성공 시 가용 재고는 즉시 감소한다.
- 동일 사용자가 같은 이벤트에 유효한 점유 또는 결제 완료 주문을 둘 이상 가질 수 없다.
- 점유에는 만료 시각이 있으며 결제 성공 전에 만료되면 재고를 복구한다.
- 결제 성공과 점유 만료가 경합하면 한쪽 상태 전이만 성공해야 한다.

### 4.4 결제

- 애플리케이션 도메인과 외부 PG 호출 사이에 명확한 인터페이스 경계를 둔다.
- 여러 Mock PG 구현 중 설정된 전략으로 하나를 선택한다. 예: 라운드로빈 또는 고정 PG.
- 기본 실패 확률은 5%이며 설정 가능하다.
- 최소 실패 사유는 `한도 부족`, `PG 점검`, `처리 시간 초과`, `알 수 없는 오류`다.
- 실패 응답은 사용자에게 이해 가능한 메시지와 재시도 가능 여부를 제공한다.
- PG 호출이 오래 걸려도 데이터베이스 트랜잭션이나 재고 잠금을 잡은 채 기다리지 않는다.
- 타임아웃처럼 결과가 불명확한 경우 즉시 새 결제를 중복 생성하지 않고 결제 조회/복구 절차를 거친다.

### 4.5 주문 생애주기

```text
PENDING_PAYMENT --결제 성공--> PAID --티켓 발급--> COMPLETED
       |                         |
       | 결제 실패              | 취소/환불
       v                         v
PAYMENT_FAILED              REFUNDED
       |
       | 재시도(새 점유 가능 시)
       v
PENDING_PAYMENT

PENDING_PAYMENT --점유 만료--> EXPIRED
```

- 모든 전이는 허용된 이전 상태에서만 수행한다.
- 결제 실패와 만료 시 점유 재고는 정확히 한 번 복구한다.
- `PAID` 이후 티켓 발급 실패가 발생하면 재처리 가능한 상태와 작업 기록을 남긴다.
- 주문 및 결제 상태 변경 이력은 시각, 이전/이후 상태, 사유와 함께 보존한다.

### 4.6 멱등성과 재시도

- 주문 생성 요청은 클라이언트가 보낸 `Idempotency-Key`를 요구한다.
- 같은 사용자, 같은 키, 같은 요청 본문은 최초 결과를 반환한다.
- 같은 키에 다른 요청 본문을 사용하면 충돌 오류를 반환한다.
- 결제 요청도 주문 단위의 고유 결제 시도 키를 PG에 전달한다.
- 서버나 클라이언트가 타임아웃 후 재시도해도 주문·결제·재고 차감이 중복되지 않아야 한다.
- 명확한 결제 실패 시 기존 점유는 즉시 해제한다. 재시도는 같은 주문에서 새 재고 점유를 원자적으로 획득한 뒤 새 결제 시도로 진행하며, 그 사이 매진되면 재시도할 수 없다.

### 4.7 티켓 유효성과 입장

- 결제 완료 주문마다 추측하기 어려운 고유 티켓 코드를 1개 발급한다.
- 티켓 상태는 `VALID`, `USED`, `CANCELLED`를 가진다.
- 행사와 티켓 소유자, 사용 가능 기간이 일치할 때만 입장할 수 있다.
- 입장 처리는 원자적이어야 하며 동시에 여러 번 스캔해도 한 번만 성공한다.
- 환불 또는 취소된 티켓과 이미 사용한 티켓은 입장할 수 없다.

### 4.8 취소와 환불

- `VALID` 상태이고 행사 시작 전인 티켓만 고객이 환불 요청할 수 있다.
- Mock PG 환불 성공 후 주문을 `REFUNDED`, 티켓을 `CANCELLED`로 바꾸고 재고를 1매 복구한다.
- 이미 사용했거나 환불된 주문의 중복 환불을 차단한다.
- PG 환불 결과가 불명확하면 `REFUND_PENDING`으로 두고 조회/재처리한다.

## 5. 기능 요구사항

### 고객 화면

- 로그인 화면 또는 개발용 간편 로그인
- 이벤트 목록/상세와 등급별 잔여 수량
- 대기 순번, 예상 상태, 구매 가능 여부
- 등급 선택 및 구매 요청
- 결제 처리 중 표시와 중복 제출 방지
- 실패 사유, 재시도 가능 여부, 다음 행동 안내
- 주문 이력과 주문별 상태 변경 내역
- 티켓 코드/QR 및 유효 상태
- 취소/환불 요청과 결과

### 운영 화면 또는 API

- 티켓 코드 검증
- 단일 사용 입장 처리
- 전체/등급별 총재고, 점유, 판매, 환불, 잔여 현황
- 결제 성공/실패 및 실패 사유별 통계
- 주문·결제·재고 변경 이력 조회

### 관리/개발 기능

- 인증된 관리자만 실행할 수 있는 리셋 API 또는 CLI
- 리셋 후 이벤트, 재고, Mock 사용자 등 데모 데이터 복원
- 실패율, PG 지연, 타임아웃, 점유 TTL, 초기 재고를 환경 설정으로 제어
- 특정 테스트에서 결과를 재현할 수 있는 결정적 Mock 모드 제공

## 6. 비기능 요구사항

- 단일 명령으로 애플리케이션과 필요한 인프라를 실행한다.
- 여러 백엔드 인스턴스가 같은 데이터베이스/공유 저장소를 사용해도 정합성을 유지한다.
- 프로세스 로컬 메모리를 재고·멱등성·대기열의 최종 진실 공급원으로 사용하지 않는다.
- 결제 지연 중 긴 DB 트랜잭션을 유지하지 않는다.
- 주요 요청에는 요청 ID를 남기고 주문 ID, 결제 ID, 사용자 ID로 추적할 수 있어야 한다.
- 비밀값과 환경별 설정은 코드에 하드코딩하지 않는다.
- 오류 응답은 기계 판독용 코드와 사용자용 메시지를 함께 제공한다.

## 7. 권장 기술 스택과 설계

빈 저장소에서 시작하는 과제라는 전제의 권장안이다.

- 프런트엔드: React + TypeScript + Vite
- 백엔드: Java 21 + Spring Boot 3 + Gradle
- 데이터베이스: PostgreSQL
- 대기열/짧은 만료 토큰: Redis
- 로컬 실행: Docker Compose
- 테스트: JUnit 5, Testcontainers, React Testing Library, Playwright(핵심 흐름만)

PostgreSQL을 주문·재고·티켓의 최종 진실 공급원으로 사용한다. Redis는 대기열 순번과 접근 토큰처럼 재생성 가능한 데이터에만 사용한다.

재고 점유는 다음 중 하나로 구현할 수 있다.

```sql
UPDATE inventory
SET available = available - 1,
    held = held + 1,
    version = version + 1
WHERE event_id = :eventId
  AND grade = :grade
  AND available > 0;
```

영향받은 행이 1개일 때만 주문과 점유를 생성한다. 주문 생성, 점유 생성, 재고 갱신은 하나의 짧은 DB 트랜잭션으로 묶고, PG 호출은 커밋 이후 수행한다. 실패/만료 복구 역시 조건부 갱신과 고유 제약으로 한 번만 실행한다.

### 주요 데이터 모델

- `users`: 로그인 사용자
- `events`: 행사 및 판매 기간
- `ticket_grades`: 등급별 가격과 총수량
- `inventories`: 가용/점유/판매 수량과 버전
- `orders`: 사용자, 이벤트, 등급, 주문 상태, 멱등성 키
- `reservations`: 주문별 점유와 만료 시각, 해제 상태
- `payment_attempts`: PG, 요청 키, 상태, 실패 코드, 원본 응답 요약
- `tickets`: 티켓 코드, 유효/사용/취소 상태
- `admissions`: 입장 처리 시각과 처리자
- `order_status_histories`: 상태 전이 감사 기록

### 주요 API 초안

- `POST /api/auth/dev-login`
- `GET /api/events`
- `GET /api/events/{eventId}`
- `POST /api/events/{eventId}/queue`
- `GET /api/queue/{token}`
- `POST /api/orders` (`Idempotency-Key` 필수)
- `POST /api/orders/{orderId}/payments`
- `POST /api/orders/{orderId}/payments/reconcile`
- `GET /api/me/orders`
- `GET /api/me/tickets`
- `POST /api/orders/{orderId}/refunds`
- `POST /api/admissions/validate`
- `POST /api/admissions/use`
- `GET /api/admin/sales`
- `POST /api/admin/reset`

## 8. 점유 만료와 장애 복구

- 요청 시 만료된 점유를 지연 정리하는 방식과 주기적 정리 작업을 함께 사용한다.
- 여러 인스턴스가 정리 작업을 동시에 수행할 수 있으므로 DB의 조건부 상태 전이 또는 `SKIP LOCKED`를 사용한다.
- 정리 작업은 같은 점유를 여러 번 읽더라도 재고를 한 번만 복구한다.
- 서버가 PG 성공 응답을 받은 뒤 DB 반영 전에 종료될 수 있으므로 결제 조회 기반 조정(reconciliation) 작업을 제공한다.
- 사용자는 `처리 중`, `실패`, `결과 확인 중`, `재시도 가능`을 구분해 볼 수 있어야 한다.

## 9. 필수 엣지 케이스

- 재고 2매에 수십~수백 개 동시 주문
- 같은 사용자의 여러 탭 또는 동시 요청
- 같은 멱등성 키의 반복 요청과 본문 불일치
- 점유 만료 직전 결제 성공
- 결제 성공 응답 직후 서버 종료
- PG 타임아웃 후 실제 PG에서는 성공한 경우
- 실패 복구 작업의 중복 실행
- 환불 요청의 중복 실행
- 동일 티켓의 동시 입장 처리
- 판매 시작 전/종료 후 요청
- 대기열 토큰 탈취, 만료, 다른 사용자의 재사용
- 매진 후 환불로 재고가 다시 생긴 경우
- 여러 서버 인스턴스의 점유 만료 작업 동시 수행

## 10. 자동화 테스트와 검증 증거

### 단위 테스트

- 주문 상태 전이 규칙
- 결제 실패 코드와 사용자 메시지 매핑
- 점유/결제/환불 정책
- 티켓 유효성 판정

### 통합 테스트

- PostgreSQL 실제 제약과 트랜잭션을 사용하는 재고 점유
- 2매 재고에 다수 동시 요청을 보내 성공 주문이 정확히 2건인지 검증
- 같은 사용자의 동시 요청 중 최대 1건만 성공하는지 검증
- 결제 실패·점유 만료 후 재고가 정확히 원복되는지 검증
- 동일 멱등성 키 재요청이 같은 주문을 반환하는지 검증
- 결제 성공과 만료 경합에서 최종 수량 불변식 검증
- 동일 티켓 동시 스캔 시 입장 1건만 성공하는지 검증
- 환불 재시도 시 한 번만 재고가 복구되는지 검증

### E2E 테스트

- 로그인 → 대기열 → 구매 → 결제 성공 → 티켓 확인 → 입장
- 결제 실패 사유 표시 → 재시도 → 성공
- 결제 성공 → 환불 → 티켓 무효화 및 재고 복구

### 제출 증거

- 테스트 실행 결과
- 동시성 테스트 요청 수, 성공/실패 수, 최종 재고 스냅샷
- 주요 API 예시 또는 OpenAPI 문서
- 실패·재시도·입장 화면 캡처
- 설계 선택과 한계를 기록한 README

## 11. 완료 조건

- `docker compose up --build` 한 번으로 전체 서비스가 실행된다.
- 기본 데이터에 행사와 일반/VIP 재고가 노출된다.
- 로그인 사용자가 대기열을 거쳐 티켓 1매를 구매할 수 있다.
- 재고 2매 동시성 테스트에서 유료 주문은 최대 2건이며 재고 불변식이 유지된다.
- 결제 실패와 점유 만료 후 재고가 정확히 복구된다.
- 실패 사유와 재시도/복구 상태가 UI에 표시된다.
- 결제 성공 티켓만 한 번 입장 가능하다.
- 미사용 티켓의 환불과 중복 환불 방지가 동작한다.
- 자동화 테스트와 리셋 절차가 문서화되고 재현 가능하다.

## 12. 구현 계획

각 단계는 이전 단계의 검증을 통과한 뒤 진행한다.

### 0단계: 정책 확정과 골격

- 위 가정 중 등급별 수량, 구매 제한, 환불 정책 확정
- 모노레포 구조와 Docker Compose 작성
- 백엔드/프런트엔드/DB/Redis 헬스 체크 연결
- 검증: 단일 명령 실행 후 웹 화면과 API 헬스 체크 성공

### 1단계: 이벤트 카탈로그와 인증

- 이벤트, 등급, 재고 스키마 및 데모 데이터
- 개발용 로그인과 사용자 식별
- 이벤트/잔여 재고 조회 API 및 화면
- 검증: 재시작 후에도 DB 데이터와 화면 조회가 일치

### 2단계: 원자적 재고 점유와 주문

- 주문, 점유, 이력 테이블과 상태 전이
- 조건부 재고 갱신, 1인 제한, 멱등성 키
- 동시성 통합 테스트 우선 작성
- 검증: 재고 2매에 다수 요청 시 성공 2건, 초과 판매 0건

### 3단계: Mock 결제와 실패 복구

- PG 인터페이스와 복수 Mock PG 구현
- 실패율/지연/실패 사유 결정적 제어
- 결제 성공, 실패, 타임아웃, 조회 조정 처리
- 사용자 실패 UI와 재시도 흐름
- 검증: 각 실패 시나리오에서 상태, 메시지, 재고가 기대값과 일치

### 4단계: 점유 만료와 다중 인스턴스

- 만료 정리 작업과 지연 정리
- 정리 작업 중복 실행 방지
- 백엔드 2개 이상 인스턴스에서 동시성 테스트
- 검증: 만료와 결제 경합 후에도 재고 불변식 유지

### 5단계: 대기열과 입장 제어

- Redis 기반 순번, 활성 토큰, 만료
- 구매 API에서 대기열 토큰 검증
- 티켓 발급, 검증, 1회 입장 처리
- 검증: 순번대로 구매 기회를 얻고 동일 티켓 동시 입장은 1건만 성공

### 6단계: 환불, 이력, 운영 현황

- 환불 상태와 Mock PG 환불
- 재고 재판매, 티켓 무효화, 중복 환불 방지
- 주문 이력과 관리자 판매 현황
- 검증: 환불 재시도 후에도 재고는 정확히 1만 증가

### 7단계: 제출 품질 마감

- 핵심 E2E 테스트와 부하/동시성 테스트 스크립트
- 관리자 리셋 수단과 인증 보호
- README에 실행법, 설정, 설계 흐름, Mock 범위, 제한사항 기록
- 검증: 깨끗한 환경에서 문서만 따라 실행·리셋·테스트 가능

## 13. MVP 범위 밖

- 실제 PG 및 실제 환불 연동
- 실명 인증, OAuth, 개인정보 처리
- 좌석 배정
- 메시지 브로커를 활용한 대규모 비동기 아키텍처
